Backend Infrastructure PRD · v1.0

Backend Infrastructure PRD

Netlify hosts the static app and serverless functions; Supabase provides Postgres, realtime channels, and storage. One stack, no servers to run, everything the orb shows is derivable from Postgres.

  • Clients subscribe to Supabase Realtime directly (anon key + RLS); writes go through Netlify Functions only — the service-role key never reaches the client.
  • The scoring engine is a pure function inside a Netlify Function — no queue in v1; compute on a 6×~50-slot grid is milliseconds.
  • Environments: main → production, deploy previews per PR. Supabase: separate prod + staging projects; migrations via supabase db push in CI.

3 · Scoring engine — deterministic, versioned, LLM-free

  • Candidates: cells where every required invitee painted free or if-need-be. If none → 2f negotiation path.
  • Score = w1·free_ratio + w2·all_DMs_present + w3·attendance_ratio + w4·workhours_fit − w5·if_need_be_count. workhours_fit penalizes slots outside any participant's local 8am–7pm (the "London guard").
  • Soft quorum: slots failing (all DMs + ≥50% when >3 invitees) are still proposable but flagged below_quorum → amber warning chip in UI.
  • Weights live in scoring.v1.json in the repo — versioned, auditable, no drift (assumed pick). Every proposal stores the weights version in breakdown_json.
  • All user-facing copy is templates keyed on breakdown fields. Nothing free-form is generated.

5 · Realtime — the orb is a subscription

  • Channel meeting:{id} broadcasts {state, responses, total, below_quorum}. Clients derive motion locally: speed = f(1 − responses/total), density ∝ responses, palette from state — one source of truth, no animation params over the wire.
  • Graph positions are client-side physics; only semantic drops (cluster membership changes) persist via graph_nodes.

6 · Auth, security, retention

  • Guest-first: every participant link carries a signed token (hashed at rest). Magic-link claim (via Resend) attaches a Supabase auth user and re-parents history.
  • RLS enforces the privacy split (assumed pick): invitee tokens can select aggregate views only (a Postgres view with count-per-cell); organizer tokens reach per-person paints. The same policy set is the v2 blob-membership boundary.
  • Google OAuth tokens: organizer-only in v1, encrypted at rest (pgsodium), minimal scopes (see Integrations §1).
  • Retention: guest paints + emails anonymized 90 days after lock (assumed pick); events audit log keeps type + timestamps only after anonymization.
  • Rate limits on token-bearing endpoints; webhook endpoints verify Google channel tokens; no CORS beyond the site origin.
